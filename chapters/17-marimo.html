17  Notebooks with Marimo

In Chapter 16, you wrote Python scripts that connect to DuckDB and run SQL queries. Scripts are powerful for automation, but they have a limitation: to see results, you have to run the whole file, read the terminal output, edit the file, and run it again. That cycle is fine for production code, but it’s slow for exploration. When you’re investigating a dataset, trying different aggregations, and iterating on your analysis, you need a faster feedback loop.

Computational notebooks solve this problem. A notebook is a document that interleaves code, output, and narrative. You write code in individual cells, run each cell independently, and see the results immediately below. This makes notebooks ideal for interactive data exploration, for building analyses incrementally, and for presenting your findings alongside the code that produced them.

This chapter introduces Marimo, a modern notebook tool that addresses the reliability problems that have plagued traditional notebooks. Marimo’s reactive execution model and strict variable rules produce notebooks that are reproducible by design, not by discipline. You’ll also discover that Marimo has native SQL cells that connect directly to DuckDB, making it the natural home for the SQL-Python workflow you started building in the previous chapter.

17.1 What Are Computational Notebooks?

A computational notebook is a document that combines three things: executable code, the output that code produces, and written explanations that provide context. Instead of writing a script in one file and reading its output in the terminal, you work in a single environment where code and results live together.

Notebooks emerged from scientific computing, where researchers needed to document their analysis process alongside the results. The idea is simple: a colleague (or your future self) should be able to read a notebook and understand not just what you found but how you found it, the queries you ran, the transformations you applied, and the reasoning behind your choices.

17.1.1 Notebooks vs. Scripts

Both notebooks and scripts are valid tools, but they excel at different tasks:

The key insight is that these are different tools for different stages of your workflow. Use notebooks when you’re exploring data and building your analysis. Use scripts when you’re automating a pipeline or building reusable functions. In practice, many workflows start as a notebook (where you figure out the right queries and transformations) and mature into scripts (where you package those steps for repeated execution).

17.2 Why Marimo?

If you’ve heard of Jupyter notebooks, you might wonder why this course uses Marimo instead. Jupyter is the most popular notebook tool, but it has well-documented problems that make it unreliable for serious work.

17.2.1 The Hidden State Problem

In traditional notebooks like Jupyter, cells share a global namespace. You can run cells in any order, delete cells, and redefine variables without the notebook tracking what happened. This leads to hidden state: the notebook’s results depend on the order you happened to run cells in, which might not match the order they appear on screen. A notebook that works when you run it interactively can produce different results (or errors) when someone runs it from top to bottom.

Marimo eliminates this problem with two design decisions.

Reactive execution. When you change a cell, Marimo automatically re-executes every cell that depends on its output. If cell A defines revenue = 1000 and cell B uses revenue, changing cell A automatically updates cell B. You never have stale results.

The one-definition rule. Each variable can be defined in exactly one cell. If cell A defines revenue and you try to define revenue again in cell C, Marimo raises an error. This prevents the “which revenue is current?” confusion that plagues Jupyter notebooks.

These constraints might feel restrictive at first, but they’re the same principles behind good software design: clear dependencies, no hidden state, and reproducible behavior. A Marimo notebook produces the same results every time, regardless of the order you edited cells during your session.

17.2.2 Marimo Notebooks Are Python Files

Unlike Jupyter notebooks, which are stored as JSON files, Marimo notebooks are stored as .py files. This has significant practical benefits: they produce clean diffs in Git, they can be run as scripts from the terminal, and they can be opened in any text editor. When you version a Marimo notebook with Git, the history shows exactly what code changed, not buried JSON metadata.

17.3 Installing Marimo

Install Marimo following the instructions in Appendix I. For now, use the standalone tool installation (uv tool install marimo). In the Production module (Chapter 21), when you structure your project as a proper package, you’ll switch to the project dependency approach.

17.4 Your First Marimo Notebook

Create and open a new notebook:

terminal
marimo edit notebook.py

Marimo opens in your browser. You’ll see an empty notebook with a single cell.

17.4.1 Creating Cells

Click in the cell and type a Python expression:

marimo
import duckdb
conn = duckdb.connect("data/northwind.duckdb", read_only=True)

Press Ctrl+Enter (or Cmd+Enter on macOS) to run the cell. Marimo executes the code and shows any output below the cell. Now create a new cell below (click the + button or press Ctrl+Shift+Enter after running) and use the connection:

marimo
result = conn.sql("""
    SELECT category_name, COUNT(*) AS product_count
    FROM products
    JOIN categories ON products.category_id = categories.category_id
    GROUP BY category_name
    ORDER BY product_count DESC
""")
result.pl()

The Polars DataFrame renders as a formatted, interactive table in the notebook output. This is the feedback loop that makes notebooks powerful: you write a query, see the results instantly, and iterate.

17.4.2 Markdown Cells

Click the cell type selector and choose Markdown (or use the keyboard shortcut) to create a narrative cell:

marimo
# Northwind Category Analysis

This notebook explores the Northwind product catalog,
examining how products are distributed across categories
and identifying pricing patterns.

Markdown cells render as formatted text, creating a document that weaves explanation with code and results. This is the communication power of notebooks: the analysis and the story exist in the same place.

17.4.3 Reactivity in Action

To see Marimo’s reactive model, create three cells:

marimo
# Cell 1: Define a threshold
min_price = 20
marimo
# Cell 2: Query products above the threshold
expensive = conn.sql(f"""
    SELECT product_name, unit_price
    FROM products
    WHERE unit_price > {min_price}
    ORDER BY unit_price DESC
""").pl()
expensive
marimo
# Cell 3: Count the results
f"Found {len(expensive)} products above ${min_price:.2f}"

Now go back to Cell 1 and change min_price to 50. When you run Cell 1, Marimo automatically re-executes Cells 2 and 3 because they depend on min_price. The table updates, the count updates, and you see the new results immediately, with no manual re-running.

17.4.4 The Cell Dependency Graph

Marimo tracks which variables each cell reads and writes, building a dependency graph. You can view this graph in the notebook interface to understand the relationships between cells. The graph also determines execution order: Marimo runs cells in dependency order, not in the order they appear on screen. This means you can arrange cells for readability (explanation first, implementation second) without worrying about execution order.

17.5 SQL Cells in Marimo

Marimo has a native SQL cell type that connects directly to DuckDB. Instead of writing conn.sql(...) in a Python cell, you write SQL directly and Marimo handles the connection and result conversion.

To create a SQL cell, click the cell type dropdown and select SQL. The SQL cell has two configuration fields at the top: a database dropdown where you select which database connection to use, and an output variable field where you name the Python variable that will hold the query result. If you’ve already created a DuckDB connection in a Python cell (like the conn variable from earlier), Marimo automatically discovers it and makes it available in the dropdown.

marimo SQL cell
SELECT
    c.category_name,
    ROUND(SUM(od.unit_price * od.quantity * (1 - od.discount)), 2) AS revenue,
    COUNT(DISTINCT o.order_id) AS order_count
FROM order_details AS od
JOIN orders AS o ON od.order_id = o.order_id
JOIN products AS p ON od.product_id = p.product_id
JOIN categories AS c ON p.category_id = c.category_id
GROUP BY c.category_name
ORDER BY revenue DESC

With the database set to your DuckDB connection and the output variable set to category_revenue, the result is automatically assigned as a Polars DataFrame. You can then use it in a Python cell:

marimo
# This cell uses category_revenue from the SQL cell above
total = category_revenue["revenue"].sum()
f"Total revenue across all categories: ${total:,.2f}"

The power of this approach is that SQL and Python cells participate in the same reactive graph. If you change the SQL query, the downstream Python cells automatically re-execute with the updated data.

17.5.1 Chaining SQL and Python

You can chain SQL cells with Python cells to build a multi-step analysis:

  1. SQL cell → Joins and aggregates raw data → outputs raw_revenue
  2. Python cell → Computes derived columns (growth rates, percentages) → assigns to enriched
  3. SQL cell → Queries the enriched DataFrame for specific patterns → outputs flagged
  4. Python cell → Formats and displays the final results

Each step uses the tool best suited to its task: SQL for joins and aggregations, Python for custom computations and formatting. Marimo’s reactivity ensures the whole chain updates when any upstream cell changes.

17.6 Interactive Features

Marimo provides UI elements that make notebooks interactive. The mo.ui module (where mo is Marimo’s standard import alias) offers dropdowns, sliders, text inputs, and other controls that bind to Python variables.

marimo
import marimo as mo

category_dropdown = mo.ui.dropdown(
    options=category_revenue["category_name"].to_list(),
    label="Select a category",
)
category_dropdown

This creates a dropdown menu in the notebook. When the user selects a value, Marimo assigns it to category_dropdown.value and re-executes any cell that depends on it:

marimo
# This cell re-executes when the dropdown selection changes
selected = category_dropdown.value

if selected:
    filtered = category_revenue.filter(
        category_revenue["category_name"] == selected
    )
    filtered

Interactive elements turn a static analysis into an explorable tool. A stakeholder can select different categories, adjust thresholds, or filter date ranges without touching any code.

TipInteractive elements for exploration

Interactive elements are most useful during the exploration and presentation phases of your work. When you’re investigating data, a slider that adjusts a threshold is faster than editing a variable and re-running. When presenting to stakeholders, a dropdown that lets them explore different categories makes the analysis more engaging than a static report.

17.7 Organizing a Notebook

A well-organized notebook tells a clear story. Here are principles that keep notebooks maintainable.

17.7.1 Cell Ordering for Readability

Because Marimo determines execution order from the dependency graph, you can arrange cells for readability rather than execution order. A common pattern is to put the narrative and high-level results at the top, with implementation details further down. The reader sees the story first, and the supporting code is available if they want to dig deeper.

17.7.2 Markdown for Narrative

Use Markdown cells liberally to explain your reasoning. Good notebooks answer three questions: What question are you investigating? (stated at the top), How did you approach it? (explained alongside the code), and What did you find? (highlighted in the results).

17.7.3 When to Refactor to a Script

Notebooks are for exploration, not for building libraries. If you find yourself wanting to import functions from a notebook into another file, it’s time to extract those functions into a .py module (like the northwind_data.py from Chapter 16) and import them into your notebook. The notebook calls the module’s functions; the module doesn’t depend on the notebook.

A good heuristic: if a cell contains a reusable function with no UI elements or display logic, it probably belongs in a module. If a cell connects data to a visualization or formats output for presentation, it belongs in the notebook.

Summary

Marimo notebooks provide a reactive environment where code, output, and narrative coexist. The reactive execution model ensures that downstream cells always reflect the current state of upstream cells, eliminating the stale-state bugs that make traditional notebooks unreliable. The one-definition rule prevents the “which version of this variable is current?” confusion.

SQL cells connect directly to DuckDB, letting you write SQL queries that produce Polars DataFrames without any boilerplate code. Interactive UI elements turn static analyses into explorable tools. And because Marimo notebooks are .py files under the hood, they integrate cleanly with Git and the rest of your development workflow.

In the next chapter, you’ll learn Polars, the DataFrame library that bridges the gap between SQL query results and Python computation. The DataFrames that SQL cells produce in Marimo are already Polars DataFrames, so you’re well positioned to work with them.

Glossary

cell
A unit of code in a notebook. Each cell can be run independently and produces its own output.
computational notebook
A document that interleaves executable code, output, and narrative text. Used for interactive data exploration and analysis communication.
dependency graph
The network of relationships between cells in a Marimo notebook, determined by which variables each cell reads and writes. Marimo uses this graph to determine execution order and reactive updates.
one-definition rule
Marimo’s constraint that each variable can be defined in exactly one cell. Prevents ambiguity about which cell “owns” a variable.
reactive execution
Marimo’s execution model where changing a cell automatically re-executes all cells that depend on its outputs. Ensures results are always current.
SQL cell
A Marimo cell type that executes SQL directly against a database connection. Results are assigned to a Python variable as a Polars DataFrame.
